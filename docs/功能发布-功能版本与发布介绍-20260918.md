# 功能发布：功能版本、发布日期与发布介绍

> 日期：2026-09-18
> 范围：合并方案 C / `docs/交接-功能发布系统合并-20260913.md` 阶段 2（发布介绍）＋ Release Note 侧首发版本回填
> 状态：模型、API、回填脚本、前端页面与契约测试均已落地并通过测试；**未对正式库执行任何写入**

---

## 一、解决了什么

在此之前，「某个功能是在哪个版本发布的」只能靠人逐个翻 Release Note：候选依据检索不认「哪个版本」这个意图，
实测 `Auto B-Line 是哪个版本发布的？` 的 top5 全是白皮书、一条 Release Note 都没有；`VAid IVC` 的问句还会把
1.14.21（补丁修复）排在 1.14.20（首次引入）之前。

现在功能版本是一等实体：

- 一行 `feature_versions` = 某个功能在某个软件版本、某个产品系列里的一次变化；
- 首发版本 = 该功能**已确认**记录里版本键最小的那一条，由 SQL 排序得出，不再每次从 PDF 重新推导；
- 每条记录带证据（资料 ID、页码、原文摘录、命中方式、证据类型）与复核状态；
- 发布介绍挂在功能版本上，按 A 侧口径分四个字段保存并留历史。

## 二、数据模型（4 张新表，全部为增量新表）

| 表 | 关键列 | 说明 |
|---|---|---|
| `feature_versions` | feature_id、software_version、`version_sort_key`、product_series、market、`release_date`、change_type、`configuration_status`、`lifecycle_status`、evidence_*、source、review_status | `UNIQUE(feature_id, software_version, product_series, market)` |
| `release_introductions` | feature_version_id（唯一）、summary、clinical_significance、workflow、applications_json、version、review_status | 与功能版本一对一 |
| `release_introduction_revisions` | introduction_id、version、四个内容字段、review_status | `UNIQUE(introduction_id, version)`，每次保存前快照上一版 |
| `release_introduction_attachments` | introduction_id、file_name、file_path、sha256、mime_type、file_size | 附件是独立实体，不再塞进正文 JSON |

要点：

- `version_sort_key` 把版本号规范化（`1.4.80` < `1.14.20` < `1.14.100`），数字版本排在文本版本之前，
  因此 `R10` 这类文本版本不会冒充首发版本。
- 变更类型 `added / optimized / fixed / removed / status_changed / unknown`；
  证据类型 `configuration_change`（配置变更表）/ `narrative`（正文叙述）/ `manual`。
  **只有「配置变更表 + 新增」才算首发候选**，正文里的「优化」只说明该版本涉及该功能。
- `configuration_status` 保留 Release Note 原文口径（选配/标配/招标支持/未注册），`lifecycle_status`
  沿用 A 侧的 6 态（未定义/开发中/待确认/已发布/已下线/已废弃），转换表写在代码里而不是可改的配置表里。
- 候选一律 `review_status='pending'`，人工确认后才进入正式结论。

## 三、API（`/api/release`）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/features/{feature_id}/versions` | 功能发布时间线 + 首发版本 + 首发候选 + 覆盖边界说明 |
| GET | `/versions?software_version=&product_series=&review_status=&q=` | 某个版本发布了哪些功能 |
| GET | `/overview` | 按软件版本汇总（已确认/待复核计数） |
| POST | `/features/{feature_id}/versions` | 手工登记 |
| PUT / DELETE | `/versions/{id}` | 修改（含复核状态、发布日期）/ 删除（同时回收附件文件） |
| GET / PUT | `/versions/{id}/introduction` | 读取 / 保存发布介绍（未传的字段保持原值） |
| GET | `/versions/{id}/introduction/history` | 全部历史版本，当前版标记 `is_current` |
| POST | `/versions/{id}/introduction/attachments` | 上传附件 |
| DELETE | `/introduction-attachments/{id}` | 删除附件并回收文件 |
| GET | `/evidence-documents` | 可作为依据的 Release Note 清单 |
| POST | `/backfill` | 生成候选；`apply=false` 只预览，`apply=true` 才落库 |

## 四、回填规则（`app/services/feature_release_backfill.py`）

1. **匹配键分层**：V 代码 > IPN > 中英文名称；英文名要求 ≥3 字符并加词边界，避免 `SMF` 之类误命中；命中方式随候选返回。
2. **章节状态按行跟踪**：抽取器把整页压平成一个 chunk（常见 `1 / 1. 概述 / 2. 配置变更` 同块），
   只看首行会把所有表格行误判为正文；状态逐行判定并跨 chunk 传递。
3. **目录行不作为证据**：带点前导 + 页码的行（`3.5.4. Added CBI mode to enable SMF function NEW ...... 8`）只是章节列表。
   实测未加这条规则时，15 条「首发候选」里有 5 条是目录行；加上之后降到 10 条且全部是带 V 代码的配置变更行。
4. **「资料中最早出现」≠「首发」**：结果里同时返回 `earliest_ingested_version`（已纳管 Release Note 最早版本）与
   `coverage_note`，页面上以警示条展示。
5. 回填**只写候选**：默认 dry-run，`--apply` 才写入，写入即 `review_status='pending'`、`source='release_note'`，且幂等。

## 五、已实测的数据结论（正式库只读副本）

- 正式库副本上 dry-run：**150 条候选，其中 10 条首发候选**，命中方式全部是 V 代码，
  例如 SMF@1.14.80、VATT@1.14.80、Vaid Nerve@1.14.80、Live Track@1.14.70；耗时 1.2 秒。
- 证据抽取（独立只读复核）：34 份 Release Note 共 **338 条配置变更行**（310 条含 V 代码）；
  其中 **105 条来自 1.51.21 的「整机完整配置矩阵」**——那是当时的配置结果而非增量，
  这些行在分类里是 `status_changed`，不会被当成首发候选。
- **34 份 Release Note 正文与文件名都没有发布日期**（严格日期模式 0 命中）。
  → 发布日期无法从现有资料回填，`release_date` 只能由产品负责人确认后人工填写，页面已明确提示。
- 已知资料缺口（不影响本次交付，但影响回填可信度）：`ULTIMUS 9E 1.50.11 / 1.50.12` 中文册正文抽取失败
  （chunk 只剩项目符号），这两份的配置变更表无法从库内文本获得；`1.51.35`、`1.14.21` 本身没有配置变更章节。

  移植时应做真渲染或明确降级为章节目录配置，不要保留空壳。
- **未移植** A 的 `parameters`、`requirement_docs`、`design_docs`、用户/权限（D1 裁定不合并）。
- 附件落在 `backend/release_attachments/`（已加入 `.gitignore`），文件名用 uuid + 后缀，
  原始名只作展示：避免 macOS NFD 归一化与重名；传入文件名仍走路径穿越校验（见交接文档第七节要求）。
- 前端页面：`frontend/src/views/FeatureRelease.vue`，菜单「功能发布」，四个页签
  （功能版本查询 / 按版本查询 / 发布介绍 / 候选回填）。

## 七、如何运行

```bash
# 1) 建表：后端启动时 init_db() 会自动补齐这 4 张新表（只建新表，不动已有数据）
cd backend && python3 -m uvicorn main:app --host 0.0.0.0 --port 8086 --reload

# 2) 回填（默认 dry-run，先对副本执行）
cp backend/product_config.db /tmp/release_check.db
python3 backend/scripts/backfill_feature_versions.py --database /tmp/release_check.db
python3 backend/scripts/backfill_feature_versions.py --database /tmp/release_check.db --apply

# 3) 测试
cd backend && python3 -m pytest tests/ -q
cd frontend && npm test
```

已验证：对正式库副本执行 `create_all` 只新增上述 4 张表，`features / config_items / config_values /
knowledge_documents / knowledge_document_chunks / config_versions` 行数完全不变。
