# 待审核数据的批量处理（2026-09-18）

> 背景：产品负责人问「系统里到底有多少待审核数据，每个版本都要逐条审吗」。
> 审计结论见下，本次交付只解决「逐条审」的效率问题；**未对正式库执行任何写入**。

当前生效版本（batch 5）待修正 **0** 条。跨版本对照证明它们是规则迭代的残留：
82 条对应的原始行在 batch 4/5 里已经是 `auto_ready`（79 条）或 `excluded`（3 条）。

**10 行 / 9 个功能**，不是 150 行。

## 二、本次交付：按问题类型 / 按变更维度批量复核

### 数据审核侧

| 接口 | 用途 |
|---|---|
| `GET /api/knowledge/review-items/issue-summary?data_type=&batch_id=` | 按 issue_code 汇总一个批次的待修正条数（一行带多个问题码时在每类下各计一次） |
| `POST /api/knowledge/review-items/batch-confirm` | 按 issue_code / item_ids / source_refs 批量确认或排除 |

### 功能发布侧

| 接口 | 用途 |
|---|---|
| `POST /api/release/versions/batch-review` | 按 `software_version` / `change_type` / `evidence_kind` / `first_candidate_only` / `version_ids` 批量确认或驳回 |
| `GET /api/release/versions/{id}/revisions` | 一条功能版本的全部留痕 |

`first_candidate_only=true` 用的是与回填预览 `is_first_release_candidate` 完全相同的
口径（每个功能 + 系列范围内最早一条「配置变更表 + 新增」），所以界面上标着
「首发候选」的行与批量动作命中的行不会出现口径差。

### 共用纪律

1. **默认只预览**：`dry_run=True` 是默认值，显式 `dry_run=false` 才落库——与候选回填同一套纪律。
2. **只动待处理行**：数据审核只处理 `needs_review`，功能版本只处理 `pending`；
   已自动可用 / 已确认 / 已驳回的记录不会被批量动作覆盖。
3. **批量不写值**：数据审核批量只允许「已确认 / 已排除」。改内容必须逐条修正，
   否则会把整类行写成同一个值。
4. **冻结批次先拒绝**：冻结原因优先于「没填修改人」，避免用户填完才发现改不了。
5. **超限需确认条数**：命中超过 50 条时必须回传相同的 `confirm_count`，防手滑。
6. **每行各留一条痕迹**（本次新增 `feature_version_revisions` 表）：
   功能版本的登记、单条修改、单条确认/驳回、批量确认/驳回都写一条不可变快照，
   含 `before_json` / `after_json` / `action` / `change_note` / `changed_by`。
   批量动作的 `change_note` 写成「批量确认｜口径：首发候选 / 版本 X / 变更类型 Y｜本次 N 条」，
   单条与批量在 `action` 上区分（`confirmed` vs `batch_confirmed`）。
   数据审核侧的留痕沿用既有 `data_review_revisions`（`action` 仍记审核状态本身，
   批量口径写在 `change_note` 里），`before_payload == after_payload`，原文与识别值不变。

### 前端入口

- 注册管理 → 数据审核中心：批次摘要下方新增「按问题类型批量处理」，
  每类问题一行（标签 + 条数 + 「确认这类 / 排除这类」）；点击先弹预览明细，
  必填修改人后才能写入；冻结批次按钮禁用并写明原因。
- 功能发布 → 按版本查询：新增「批量确认 <版本> 待复核」与「确认首发候选」；
  页面顶部新增「操作人」输入框，单条确认 / 驳回也会写进留痕。
